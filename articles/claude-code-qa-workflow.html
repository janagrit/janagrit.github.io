How I test with Claude Code

Iana Grytsenko · October 13, 2026 · 5 min read

I use Claude Code every day, but I don’t let it decide what “done” means. The AI writes a lot of my test code. My job is the system around it: the order things happen in, the checks that catch its mistakes, and the review before anything is merged. This is that system.

Claude Code runs inside VS Code. On top of it I use a set of open-source skills: reusable instructions for jobs like test-driven development or running a full verification pass. A skill is installed once on my machine, and then I can call it by name in any project.

01The first ten minutes decide the next ten weeks

Before any test gets written in a new project, I do four things:

  1. Get a tour. I ask Claude to map the project: how it’s structured, how to run it, where the risky parts are. I read the answer against the code, because a wrong mental model at this stage costs days later.
  2. Write down the rules. The /init command creates a CLAUDE.md file with the run commands and conventions. Claude reads it at the start of every session, so I don’t repeat myself and it doesn’t forget.
  3. Keep junk out of git. A .gitignore for dependencies, virtual environments, test reports and secrets goes in before the first commit. If Source Control suddenly shows thousands of changes, something wasn’t ignored.
  4. Commit a clean starting point, so every later step can be undone.

02Tests first, even when the AI writes them

AI is very good at writing a test that passes. That’s exactly the problem: a test that has never failed proves nothing. So for every feature or scenario I ask for the failing test first, watch it fail for the right reason, and only then ask for the code.

PromptUse the tdd-workflow skill to add a smoke test for site search: write the failing test first and show me it failing, then make it pass.

On end-to-end work I also ask for page objects and fixtures from the start. A Playwright suite without structure is fast to write and slow to live with.

03Green once isn’t green

A suite that passes once can still be flaky. Before I trust new tests, I run the whole thing several times in a row and treat any test that changes its answer as a bug.

PromptUse the verification-loop skill: install dependencies, build, run every test three times, and list anything that failed even once.
This habit comes straight from real projects. On a Java and Selenium suite, fixing flaky tests at the root cut false-positive failures by 60% and made the CI results trustworthy again.

04Testing AI needs its own rules

When the thing under test is an AI agent, “does it pass?” becomes “how often does it misbehave, and is that getting worse?”. Two practices matter most:

  • Attack it on purpose. I design adversarial scenarios: trying to make the agent reveal data it shouldn’t, ignore its instructions, or invent answers. Each one gets a metric that fails on a real leak.
  • Lock in a baseline. Today’s scores become the floor. If a prompt or model change drops any metric below it, the build fails.

My AI agent evaluation demo does both: a strict voice agent contains 10 out of 10 attacks, a deliberately weak one leaks as a control, and a regression gate runs on every pull request.

05Nothing merges unreviewed, including AI code

Before every commit I run /code-review, then read the diff myself. I review AI-written tests the way I review a colleague’s: does each assertion check something that matters, and would this test fail if the feature broke?

07What this looks like in practice

The same steps, in a different order for each kind of project:

  • A test suite for a company website, like my Uptic Hospitality audit: project setup with page objects, smoke tests written test-first, accessibility and visual checks, a three-run flakiness pass, review, then CI on every push.
  • An AI evaluation project: record the starting scores, look for missing failure modes, add each scenario test-first, then lock in the baseline.
  • A live app I test, like Kids Nearby: end-to-end tests for the main user flows, a full verification run, then a check of the live site on real screen sizes.

08The short version

Let the AI write. Make it prove the test can fail. Run everything more than once. Give AI quality a floor it can’t drop below. Read every diff before it merges.
